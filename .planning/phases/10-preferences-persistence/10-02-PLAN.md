Wait — we can't reference `preferences` before it's declared as a property. And we need both `store` and `preferences` to exist. The issue is that JobStore needs the PreferencesStore reference.

Solution: Create `preferences` first, then create `store` with it:

Change line 15 from:

To:
```swift
@StateObject private var preferences = PreferencesStore()

}
```

Wait, that changes store from @StateObject to a computed property. That breaks @StateObject semantics. SwiftUI requires @StateObject for ObservableObject lifecycle management.

Better approach: Initialize both in an init(), or use a lazy pattern. But AutomationHealthApp is a struct (App protocol), and @StateObject has a specific init pattern.

The cleanest approach: Use `StateObject(wrappedValue:)` with explicit init:

```swift
@main
struct AutomationHealthApp: App {
    @NSApplicationDelegateAdaptor(AppDelegate.self) private var appDelegate
    @StateObject private var preferences = PreferencesStore()
    @StateObject private var store: JobStore

    init() {
        let prefs = PreferencesStore()
        _preferences = StateObject(wrappedValue: prefs)
        _store = StateObject(wrappedValue: JobStore(preferences: prefs))
    }

    var body: some Scene {
        // ...
    }
}
```

This creates PreferencesStore once, passes its reference to JobStore, and both are properly @StateObject-wrapped.

PreferencesStore.didSet writes whatever the slider produces — but slider can't produce out-of-range values. |
| T-10-06 | Information Disclosure | Settings scene visibility | accept | Settings window is a standard macOS feature — no sensitive data displayed. Grouping mode names, scan depth, and result count are non-sensitive configuration values. No authentication required to open Settings. |
| T-10-07 | Spoofing | UserDefaults write path | accept | Same threat as T-10-04 in Plan 01. Settings view writes to UserDefaults via PreferencesStore.didSet; same macOS sandbox boundary applies. |
