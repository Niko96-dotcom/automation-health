# Phase 10 — UI Design Contract

> Visual and interaction contract for preferences persistence and native macOS Settings scene. Generated by gsd-ui-researcher.
> Platform: macOS SwiftUI app. No CSS/web tokens — design contract is about native control layout, labels, and interaction behavior.

---

## Design System

| Property | Value |
|----------|-------|
| Tool | none (native SwiftUI) |
| Preset | not applicable — no web component library |
| Component library | SwiftUI + AppKit (native macOS) |
| Icon library | SF Symbols (system) |
| Font | System (SF Pro) |

**Rationale:** This is a native macOS SwiftUI app targeting macOS 14+. It uses zero third-party Swift packages. All UI is built with SwiftUI system views (`Form`, `Picker`, `Toggle`, `Slider`, `Settings` scene). No design system tooling is needed.

---

## Spacing Scale

This phase adds a **Settings scene** using native SwiftUI `Form` with `.formStyle(.grouped)`. The form inherits macOS system spacing — no custom spacing tokens are introduced.

| Token | Value | Usage |
|-------|-------|-------|
| Default section spacing | System-defined | Between form sections — SwiftUI `.formStyle(.grouped)` handles |
| Row spacing | System-defined | Between fields within a section — native `Form` behavior |
| Window padding | 20pt | Settings window outer padding — `Settings` scene default |

**Exceptions:** New `SettingsView` uses a `.frame(width: 480)` constraint to match macOS Settings scene convention. No other explicit spacing overrides.

**Source:** Native SwiftUI defaults. No project tailwind/CSS tokens exist (this is a SwiftPM macOS app).

---

## Typography

Settings scene uses **system fonts exclusively** — no custom font sizes or weights are introduced.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body (form labels, values) | System `.body` | Regular (400) | System default |
| Section header | System `.headline` | Semibold (600) | System default |
| Helper/caption text | 12px | Regular | System default |

**Note:** The existing app already uses `.font(.system(size: 18, weight: .semibold))` for sheet titles (e.g., Manual Record sheet). The Settings scene does **not** follow that pattern — it uses `Form` section headers for structure, with no standalone title. This is the standard macOS Settings window convention.

**Source:** Pre-populated from existing codebase patterns (ManualRecordSheetView uses system fonts) and macOS HIG for Settings windows.

---

## Color

Settings scene uses **native macOS system colors/material** with automatic dark/light mode adaptation. No custom hex colors are introduced.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | System window background | Settings window background — automatic via `.windowBackground` |
| Secondary (30%) | System grouped form background | Form sections — automatic via `.formStyle(.grouped)` |
| Accent (10%) | System accent color (user's macOS accent setting) | Toggle "on" states, Slider track fill, Picker selection highlight |

Accent reserved for: **System-standard interactive controls only** — Toggle switches when on, Slider fill track, Picker selection indicator. No custom accent color is set; the app respects the user's macOS system-wide accent color preference.

**Destructive:** Not applicable — this phase has no destructive actions. No delete, remove, or reset controls exist in the Settings scene.

**Source:** Pre-populated from research/STACK.md which confirms no new dependencies, native macOS UI only. System colors are implicit in SwiftUI `Form`, `Toggle`, `Slider`, `Picker`.

## Interaction Contract

### Settings Scene (Cmd+,)

| Interaction | Behavior |
|-------------|----------|
| Open Settings | `Cmd+,` or `Automation Health > Settings...` from app menu. SwiftUI `Settings` scene is added as sibling to `WindowGroup` in `AutomationHealthApp`. No custom menu wiring needed — SwiftUI handles automatically. |
| Change grouping mode | `Picker` bound to `$preferences.groupingMode` via `@ObservedObject`. Change writes to `UserDefaults.standard.set(_:forKey:)` in `didSet`. Sidebar immediately reflects new grouping. |
| Change scan-on-launch toggle | `Toggle` bound to `$preferences.scanOnLaunch`. Immediate write to UserDefaults. Takes effect on next app launch. |
| Change max depth slider | `Slider` bound to `$preferences.scanMaxDepth` (range 0–5, step 1, default 2). Immediate write to UserDefaults. Takes effect on next scan refresh. |
| Change max results slider | `Slider` bound to `$preferences.scanMaxResults` (range 10–500, step 10, default 200). Immediate write to UserDefaults. Takes effect on next scan refresh. |
| Close Settings | Standard macOS window close (red X button or `Cmd+W`). Changes are already persisted — no "Save" or "Apply" button needed. |

### Preferences Persistence Behavior

| Interaction | Behavior |
|-------------|----------|
| First launch (no preferences) | `PreferencesStore.init()` calls `UserDefaults.standard.register(defaults:)` with documented v1.1 defaults: grouping mode `.source`, collapse state empty (all expanded), scan-on-launch `true`, max depth `2`, max results `200`. |
| Preferences decoded | `PreferencesStore.init()` reads existing `UserDefaults` values. If `sidebarCollapseState` JSON decodes successfully, uses it; otherwise falls back to empty collapsed set. |
| Preferences survive app quit | All `@Published` properties write to `UserDefaults.standard` on `didSet`. No manual save needed — writes are synchronous and atomic. |
| Collapse state per grouping mode | `SidebarCollapseState` already uses `Set<SidebarSectionID>` which includes `groupingMode`. When user switches grouping modes, collapse state for new mode is restored from persisted set. Collapse state for previous mode is preserved but not visible. |

### Keyboard Shortcuts (this phase)

| Shortcut | Behavior |
|----------|----------|
| `Cmd+,` | Opens Settings scene (automatic via SwiftUI `Settings` scene declaration) |
| `Cmd+R` | Rescan automations (existing, unchanged) |

**Note:** Full keyboard navigation shortcuts (Cmd+Shift+F, expand/collapse all, grouping mode switching, jump-to-letter) are **Phase 11**. This phase only adds the Settings shortcut which comes free with the `Settings` scene.

## Settings View Layout Contract

```
┌──────────────────────────────────────────────────────────┐
│  Automat ion Health Settings                     ○ ─ ✕   │
├──────────────────────────────────────────────────────────┤
│                                                          │
│  ┌─ Default View ──────────────────────────────────┐     │
│  │                                                  │     │
│  │  Default Grouping:   ┌─────────────────────┐    │     │
│  │                       │ Source         ▾ │    │     │
│  │                       └─────────────────────┘    │     │
│  └──────────────────────────────────────────────────┘     │
│                                                          │
│  ┌─ Candidate Scanning ─────────────────────────────┐     │
│  │                                                  │     │
│  │  Scan for candidate scripts on launch    ○───    │     │
│  │  When enabled, Automation Health searches        │     │
│  │  supported script directories for automations    │     │
│  │  that may not be registered in a known          │     │
│  │  scheduler.                                      │     │
│  │                                                  │     │
│  │  Maximum Scan Depth       ───────●─────────     │     │
│  │                           Value: 2               │     │
│  │  Limits how many subdirectory levels the         │     │
│  │  candidate scanner traverses.                    │     │
│  │                                                  │     │
│  │  Maximum Results Per Scan  ──────●────────────   │     │
│  │                            Value: 200            │     │
│  │  Limits the total number of candidate records    │     │
│  │  produced by a single scan.                      │     │
│  └──────────────────────────────────────────────────┘     │
│                                                          │
└──────────────────────────────────────────────────────────┘
```

**Width:** 480pt (fixed, matches macOS Settings convention)
**Format:** Two `Form` sections with `.formStyle(.grouped)`:
1. **Default View** — Picker for default grouping mode
2. **Candidate Scanning** — Toggle for scan-on-launch, Slider for max depth (0–5), Slider for max results (10–500)

**Control bindings:**
- Picker: `$preferences.groupingMode` → `SidebarGroupingMode` (String-raw-representable, @AppStorage-compatible)
- Toggle: `$preferences.scanOnLaunch` → `Bool`
- Slider (depth): `$preferences.scanMaxDepth` → `Int`, range 0...5, step 1
- Slider (results): `$preferences.scanMaxResults` → `Int`, range 10...500, step 10

**Source:** Layout derived from CONTEXT.md D-03, D-05. Control ranges from CONTEXT.md D-03. The grouped Form pattern follows existing ManualRecordSheetView pattern at `Sources/AutomationHealth/Views/ContentView.swift:211-238`.
