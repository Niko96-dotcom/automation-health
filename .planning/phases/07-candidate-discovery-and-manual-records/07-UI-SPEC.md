# Phase 07 - UI Design Contract

> Visual and interaction contract for candidate discovery, manual records, and shared inventory presentation. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

---

## Phase Boundary

Phase 7 adds bounded candidate script records, app-only manual record create/edit/remove flows, and presentation updates so Candidate and Manual records move through the same search, sidebar, selection, and detail surfaces as scheduled and registered records.

In scope:

- Show candidate script discoveries as Candidate records with no schedule evidence.
- Add, edit, and remove Manual records through app-owned storage only.
- Make confidence and origin visible in sidebar/detail presentation.
- Update search, empty-state, toolbar, and detail copy from scheduler-only language to supported automation inventory language.
- Keep scanner IO and manual persistence behind `ActiveJobsCore` and `JobStore`; SwiftUI views must not read scheduler files, script files, or manual JSON directly.

Out of scope:

- Editing, removing, running, validating, or rewriting real scheduler jobs, scripts, Shortcuts, Automator workflows, cron entries, launchd plists, or Hermes metadata.
- User-configurable candidate scan folders or ignore rules; future preferences own that.
- Sidebar grouping modes, collapsible sections, and custom focus treatment; Phase 8 owns those.
- Inferring that a script is scheduled by reading shell history, editor history, terminal history, or broad home-directory content.

## Design System

| Property | Value |
|----------|-------|
| Tool | none |
| Preset | not applicable |
| Component library | Native SwiftUI/AppKit only |
| Icon library | SF Symbols |
| Font | macOS system font, SF Pro |

Design system notes:

- No React, Tailwind, shadcn, web registry, or third-party component system is present.
- Use existing SwiftUI `NavigationSplitView`, toolbar, sheet, form, `DisclosureGroup`, `ContentUnavailableView`, and material surface patterns.
- Do not introduce new Swift package dependencies for Phase 7 UI.
- Keep cards at the existing 8px corner radius or less. Do not nest cards inside cards.
- Use labeled buttons for record mutation. Icon-only controls require `help` and accessibility labels, but Phase 7 should prefer `Label` buttons where space allows.

## Spacing Scale

Declared values (must be multiples of 4):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Inline icon/text gaps, compact helper text gaps |
| sm | 8px | Sidebar row internal gaps, form field helper spacing, footer spacing |
| md | 16px | Default form padding, detail section padding, sheet content spacing |
| lg | 24px | Sheet edge padding, detail page vertical rhythm, empty-state padding |
| xl | 32px | Major breaks between form groups or detail groups |
| 2xl | 48px | Large empty-state breathing room |
| 3xl | 64px | Reserved for full-page empty states only |

Exceptions: none. Native macOS control intrinsic heights and SF Symbol drawing sizes are platform metrics, not custom spacing tokens.

Implementation constraints:

- Preserve stable sidebar row layout; adding confidence text must not resize rows on hover or selection.
- Use one horizontal row gap for icon/status plus copy; do not add decorative gutters.
- Manual record sheets should use one-column form layout on all window sizes, with labels aligned by native SwiftUI form behavior.

## Typography

Use exactly these type roles for Phase 7 UI additions:

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Label | 12px | 600 | 1.3 |
| Body | 14px | 400 | 1.5 |
| Heading | 18px | 600 | 1.25 |
| Display | 24px | 600 | 1.2 |

Typography constraints:

- Allowed weights: 400 regular and 600 semibold only.
- Use monospaced system text only for commands, script paths, storage paths, and raw schedule text.
- Detail header remains the only Display-scale usage for a selected record name.
- Sidebar rows use Label and Body roles only; no hero-scale text belongs in the sidebar.
- Manual form validation and helper text use Label role, secondary color, and direct wording.

## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#F5F5F2` light / `#1D1D1F` dark | Window background and broad native surfaces |
| Secondary (30%) | `#E8E8E3` light / `#2A2A2D` dark | Sidebar surface, status cards, sheets, form groups |
| Accent (10%) | `#32D583` | Primary manual-record action, selected sidebar row, focus ring, selected field emphasis |
| Destructive | `#D92D20` | Manual-record removal button and confirmation only |

Accent reserved for: `Add Manual Record`, `Create Manual Record`, `Update Manual Record`, selected sidebar row treatment, focused manual form field emphasis, and the app health pulse identity where already used. Do not use the accent for every link, all toolbar buttons, broad backgrounds, Candidate labels, or decorative fills.

Color constraints:

- Candidate and Manual confidence should be readable through text labels and SF Symbols, not through new decorative accent colors.
- Existing health colors remain semantic status indicators only: green for alive, blue for waiting, orange for stale, red for failed, gray for unknown.
- Destructive red appears only on `Remove Manual Record` and its confirmation action.
- Candidate records should use neutral material pills or labels so they do not look like warnings or proven scheduled jobs.

## Visual Hierarchy

Primary focal point:

- Detail view: selected record name, health pill, and the new Confidence card form the primary reading path.
- Manual record sheet: the `Name` field and primary create/update action are the focal points.
- Sidebar: selected row and confidence text are the focal points; section headers remain secondary.

Secondary focal points:

- Origin card in detail view.
- Candidate script path or manual notes in the configured-task section.
- Scan-note footer when candidate discovery hits bounds, unreadable locations, or ignore rules.

Icon mapping:

| Record Type | SF Symbol | Treatment |
|-------------|-----------|-----------|
| launchd | `gearshape.2` | Existing scheduled source icon |
| Hermes cron | `calendar.badge.clock` | Existing scheduled source icon |
| cron | `terminal` | Scheduled command-line source |
| Shortcuts | `command` | Registered automation source |
| Automator | `wand.and.stars` | Registered workflow source |
| Candidate scripts | `doc.text.magnifyingglass` | Possible automation candidate |
| Manual records | `square.and.pencil` | User-added app record |

Visual constraints:

- Candidate and Manual records must never share an icon treatment that implies proven scheduling.
- Detail cards should expose Source, Confidence, Origin, Health, Next Run, and Last Run where space allows. If the grid becomes dense, Confidence and Origin take priority over Source repetition.
- Candidate and Manual labels should remain legible in both light and dark appearances without relying on color alone.

## Layout Contract

### Toolbar

Use a compact primary toolbar group:

| Action | Label | Icon | Availability |
|--------|-------|------|--------------|
| Add manual record | Add Manual Record | `plus` | Always enabled unless a modal mutation is already open |
| Rescan inventory | Rescan Inventory | `arrow.clockwise` | Disabled while scanning |

Toolbar help text:

- `Add Manual Record`: "Create an app-only record for an automation the scanner cannot prove."
- `Rescan Inventory`: "Scan supported automation inventory again."

### Sidebar

Sidebar rows remain source-sectioned until Phase 8 changes grouping. Phase 7 must add enough text for evidence strength without introducing collapse or grouping controls.

Sidebar row contract:

- Primary line: `displayName`, one line, primary color.
- Secondary line: `{confidenceName} - {schedule or next run}` when inside a source section.
- Source section titles: use the `JobSource.displayName` values, including `Candidate scripts` and `Manual records`.
- Search-empty heading: "No matching automation records".
- Search-empty body: "Search by name, source, confidence, origin, command, notes, or path."

Sidebar behavior:

- Up/Down navigation continues to move through visible jobs only.
- Candidate and manual rows use the same selection model as existing records.
- Adding, editing, or removing a manual record must preserve selection when possible. After creating a manual record, select the created record.

### Detail View

Header contract:

- Title: selected record `displayName`.
- Subtitle: raw job name or manual record identifier.
- Pill: current health summary, even if unknown.
- Icon: source-specific icon from the mapping table.

Status overview cards:

| Card | Value | Detail |
|------|-------|--------|
| Health | `job.health.label` | `job.health.detail` |
| Confidence | `job.confidenceName` | `job.job.confidence.description` |
| Origin | `job.originName` | Source-independent ownership/origin |
| Source | `job.sourceName` | Raw state or source state |
| Next Run | `job.nextRunText` | Human schedule text |
| Last Run | `job.lastRunText` | Last status or no result code |

Candidate detail copy:

- Schedule text: "Script candidate (no schedule evidence)".
- Definition fallback: "Candidate script discovered at {path}."
- Last output fallback: "Candidate records do not include run output until a scheduler source proves execution."
- Reveal action label: "Reveal Script".

Manual detail copy:

- Schedule fallback: "Manual record (no schedule evidence)".
- Definition fallback: "Manual app record: {name}".
- Last output fallback: "Manual records do not include run output."
- Edit action label: "Edit Manual Record".
- Destructive action label: "Remove Manual Record".

## Manual Record Form Contract

Use a modal sheet for both create and edit.

| Field | Required | Control | Placeholder / Helper |
|-------|----------|---------|----------------------|
| Name | yes | Text field | "Weekly cleanup reminder" |
| Origin | yes | Picker/menu | Defaults to "Unknown"; options: User-authored, Third-party app, System, Unknown |
| Schedule description | no | Text field | "Every Friday morning" |
| Command or path | no | Text field | "Optional command, app, or file path" |
| Notes | no | Multiline text editor | "What this automation does and where you track it" |

Create sheet:

- Title: "Add Manual Record".
- Primary CTA: "Create Manual Record".
- Secondary action: "Discard Manual Record".
- Validation message: "Name is required before this manual record can be added."

Edit sheet:

- Title: "Edit Manual Record".
- Primary CTA: "Update Manual Record".
- Secondary action: "Discard Changes".
- Validation message: "Name is required before this manual record can be updated."

Remove confirmation:

- Title: "Remove Manual Record?"
- Body: "This removes the app-only record from Automation Health. Scheduler files, scripts, Shortcuts, Automator workflows, cron entries, launchd plists, and Hermes metadata are not changed."
- Destructive CTA: "Remove Manual Record".
- Secondary action: "Keep Manual Record".

Form behavior:

- Edit and remove controls appear only for records whose source is `manualRecords`.
- Candidate records may offer reveal-only behavior, never edit/remove controls.
- The sheet must not show fields for launchd, Hermes cron, cron, Shortcuts, Automator, or candidate records.
- Empty optional fields should not render blank labels in detail; use the fallback copy above.

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA | Add Manual Record |
| Create CTA | Create Manual Record |
| Edit CTA | Update Manual Record |
| Destructive CTA | Remove Manual Record |
| Empty state heading | No automation records yet |
| Empty state body | Rescan supported inventory or add a manual record for an automation the scanner cannot prove. |
| Filtered empty heading | No matching automation records |
| Filtered empty body | Search by name, source, confidence, origin, command, notes, or path. |
| Error state | Inventory scan failed. Review scan notes, confirm local permissions, then rescan. |
| Candidate schedule label | Script candidate (no schedule evidence) |
| Manual schedule label | Manual record (no schedule evidence) |
| Destructive confirmation | Remove Manual Record: This removes only the app-owned manual record; real scheduler files and scripts are not changed. |

Copy tone:

- Plain, local, and evidence-first.
- Use "inventory" and "automation records" instead of "jobs" when referring to the full Phase 7 surface.
- Use "Candidate" only for possible script discoveries without scheduling evidence.
- Use "Manual" only for app-owned user records.
- Never imply Automation Health can edit, repair, schedule, run, or delete real automations.

## Accessibility Contract

- All toolbar and detail actions use `Label` with text and SF Symbol.
- Candidate and Manual confidence must be present as text, not only color or icon.
- Manual form fields have visible labels and native focus behavior.
- Destructive confirmation text must explicitly say real scheduler files and scripts are not changed.
- Sidebar keyboard navigation must still work through visible rows after candidate/manual records are added.
- Detail text, paths, command fields, and notes remain text-selectable where existing detail content is selectable.

## Source And State Contract

| Concern | Contract |
|---------|----------|
| Candidate source | New `JobSource.candidateScripts` display name: `Candidate scripts` |
| Manual source | New `JobSource.manualRecords` display name: `Manual records` |
| Candidate confidence | Always `JobConfidence.candidate` unless a stronger deterministic scanner proves scheduling |
| Manual confidence | Always `JobConfidence.manual` |
| Manual storage | App-owned JSON under Application Support only |
| View IO | SwiftUI views call `JobStore`; they do not read or write scanner files, script files, or manual JSON directly |
| Selection after create | Select the created Manual record |
| Selection after edit | Keep the edited Manual record selected |
| Selection after remove | Move to the next visible record, or first visible record if needed |
| Search index | Include name, source, confidence, origin, schedule, command/path, definition, and manual notes |
