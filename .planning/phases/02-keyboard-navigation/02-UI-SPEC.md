# Phase 02 - UI Design Contract

> Visual and interaction contract for the Keyboard Navigation phase. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

---

## Design System

| Property | Value |
|----------|-------|
| Tool | none - native macOS SwiftUI contract |
| Preset | not applicable |
| Component library | SwiftUI and AppKit native controls only |
| Icon library | SF Symbols through `Image(systemName:)` and `Label` |
| Font | macOS system font through SwiftUI semantic text styles |

No third-party UI package, shadcn preset, Tailwind configuration, registry block, or new dependency is used for this phase.

## Visual Hierarchy And Interaction

| Contract | Decision |
|----------|----------|
| Primary surface | Existing left sidebar inside `NavigationSplitView`, specifically the row/list area below the sidebar search field and above the scan footer. |
| Focal point | The selected job row. Keyboard movement should make the selected row feel like the active navigation anchor while preserving the grouped source structure around it. |
| Visual hierarchy | Section headers orient scanning; job rows remain the only selectable elements; the current selected-row background remains the strongest visual cue. |
| Focus scope | Handle Up and Down only when the sidebar row/list area is focused. The search field keeps native text-editing arrow behavior. |
| Focus styling | Use subtle native focus behavior if SwiftUI provides it naturally. Do not add a custom focus ring, new accent outline, glow, or persistent focus decoration in Phase 2. |
| Row click behavior | Clicking a job row selects that row and makes the sidebar row/list area ready for immediate Up/Down navigation. |
| Navigation order | Traverse `sections.flatMap(\.jobs)` from `SidebarView`; this is the canonical visible job order after search filtering and source grouping. |
| Non-job UI | Sidebar summary, source headers, empty states, and scan footer controls are skipped because they are not part of the visible job row list. |
| Entry behavior | If no visible row is selected, Down selects the first visible job and Up selects the last visible job. |
| Hidden selection behavior | If `selectedJobID` points to a job hidden by the active search query, treat keyboard navigation like no visible selection: Down enters at the first visible job and Up enters at the last visible job. |
| Boundary behavior | Up on the first visible job and Down on the last visible job keep the current selection. Do not wrap, clear selection, or move focus away. |
| Detail synchronization | Keyboard navigation writes to the existing `selectedJobID` binding only. The detail pane continues to follow `JobStore.selectedJob`. |
| Search interaction | Search changes do not automatically move selection or replace the detail pane. Navigation after a search uses only the currently visible filtered rows. |
| Refresh interaction | Preserve `JobStore.refresh()` selection behavior. If the selected job still exists after refresh, keep it; if not, use the store's existing first-job fallback. |
| Scroll behavior | Scroll only after keyboard-originated selection changes, only enough to reveal the selected row when it is outside the viewport. Do not center every movement. |
| Out of scope | No additional shortcuts, type-ahead navigation, collapsible sections, grouping controls, job mutation controls, scanner IO in views, or redesign of the sidebar row style. |

## Typography

Use only these font sizes and weights for Phase 2 sidebar work:

| Role | Size | Weight | Line Height | Usage |
|------|------|--------|-------------|-------|
| Section label | 11px | semibold (600) | 1.2 | Existing source section headers and visible counts |
| Row title | 13px | regular (400) | 1.35 | Existing job display names |
| Row detail | 12px | regular (400) | 1.3 | Existing next-run or schedule subtitles |
| Detail heading | 17px | semibold (600) | 1.2 | Existing detail/support headings only if touched |

Use exactly two weights in this phase: regular (400) and semibold (600). Keyboard navigation must not introduce new labels, helper text, or visible shortcut instructions.

## Color

Use semantic macOS colors and materials so the sidebar adapts to Light Mode, Dark Mode, and user accent color settings.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | macOS regular material; approx. #F5F5F7 light / #1E1E1E dark | Sidebar background and root surface |
| Secondary (30%) | `Color.secondary`; approx. #6E6E73 light / #A1A1A6 dark | Section headers, counts, subtitles, footer metadata |
| Accent (10%) | `Color.accentColor`; selected background at 0.18 opacity | Selected job row background, native focus affordance if provided by SwiftUI, active sidebar affordance |
| Destructive | system red; approx. #FF3B30 light / #FF453A dark | Not used in Phase 2; reserved for future destructive warnings only |

Accent reserved for: selected job row background, native focus indication, and existing system-tinted chrome. Do not use accent color for every interactive element.

Semantic status colors remain separate from accent color:

| Status | Color |
|--------|-------|
| Healthy | system green |
| Waiting | system blue |
| Stale | system orange |
| Failed | system red |
| Unknown | system gray |

Status colors are reserved for the existing `HealthDot` and must not be repurposed as keyboard focus or navigation feedback.

## Implementation Contract For Planning

| Area | Contract |
|------|----------|
| Data boundary | Use already-presented `SidebarJobSection` and `SidebarJobSummary` values. Do not read scheduler files from views. |
| Navigation helper | Define previous/next behavior over visible row ids or `SidebarJobSummary` values, not raw `ScheduledJob` values or all store jobs. |
| Visible rows | Use `sections.flatMap(\.jobs)` as the only keyboard traversal source. |
| Selection write | Keyboard navigation updates the existing `selectedJobID` binding and does not create parallel selected-row state. |
| Focus owner | Keep search ownership in `ContentView`; scope keyboard handling to the focusable row/list area in `SidebarView`. |
| Key handling | Handle Up and Down for row navigation; do not handle Left, Right, Return, Escape, or refresh shortcuts in this phase. |
| Key repeat | Native repeat behavior is acceptable if it remains smooth and stays within the visible row list. |
| Scroll reveal | Use keyboard-originated pending selection state or equivalent gating so mouse clicks, search changes, and refresh preservation do not trigger extra scroll movement. |
| Boundary safety | Clamp at first and last visible jobs. Do not write `nil` at list boundaries. |
| Empty visible list | If there are no visible rows, Up/Down should not change selection or show a selectable placeholder. |
| Testing | Add focused coverage for pure navigation behavior if extracted into a presentation helper; otherwise use `swift build` plus manual verification notes for focus and scroll behavior. |
| Read-only boundary | Sidebar key handling must only update UI selection. It must not mutate scheduler files, job definitions, launchd state, Hermes cron metadata, or output files. |
