In `script/build_and_run.sh`, modify the Info.plist heredoc template (lines 41-63) to include the `SUPublicEDKey` entry when the `SU_PUBLIC_ED_KEY` environment variable is set.

Unlike `release.sh` (which hard-fails without the key), `build_and_run.sh` is used for local development. A developer may not have generated EdDSA keys yet, and the app should still build and run for development purposes even without Sparkle update verification working. However, if the key IS set, it should be embedded so the full auto-update flow can be tested locally.

**Strategy:** Use bash default value expansion to conditionally include the key.

**Exact change in the heredoc template (add after `NSPrincipalClass` block, before `</dict>`):**

```xml
  <key>SUPublicEDKey</key>
  <string>${SU_PUBLIC_ED_KEY:-}</string>
```

With `${SU_PUBLIC_ED_KEY:-}`, if the env var is unset, the value is empty string. Sparkle will fail `start()` gracefully (which UpdateStore already catches and shows as error state in Settings — this is the tested error-handling path from plan 14-02).

If the env var IS set, the public key is embedded and Sparkle can verify updates normally.

**Also add CFBundleShortVersionString and CFBundleVersion** (both with value "0.0.0-dev") to the dev Info.plist, AFTER the SUPublicEDKey block. This matches the fields in release.sh and ensures Sparkle has version metadata even for dev builds. The `feedURLString(for:)` in UpdateStoreDelegate already returns `nil` for dev builds, so no appcast check will occur, but having version metadata is good practice.

```xml
  <key>CFBundleShortVersionString</key>

  <string>0.0.0-dev</string>
```

**Exact insertion order** (after NSPrincipalClass, before closing </dict>):
1. `SUPublicEDKey` block
2. `CFBundleShortVersionString` block
3. `CFBundleVersion` block

Make two changes to `.github/workflows/release.yml`:

**Change 1: Add SPARKLE_EDDSA_PRIVATE_KEY injection step**

Insert a new step AFTER the "Set notarization credentials" step (line 79-83) and BEFORE the "Build, sign, notarize, and package DMG" step (line 86). The new step exports the Sparkle signing key from GitHub Secrets to the GITHUB_ENV so `script/release.sh` can read it:

```yaml
      - name: Set Sparkle signing key
        env:
          SPARKLE_EDDSA_PRIVATE_KEY: ${{ secrets.SPARKLE_EDDSA_PRIVATE_KEY }}
        run: echo "SPARKLE_EDDSA_PRIVATE_KEY=$SPARKLE_EDDSA_PRIVATE_KEY" >> $GITHUB_ENV
```

This pattern mirrors the existing "Set notarization credentials" step that also writes to GITHUB_ENV.

**Change 2: Add dist/appcast.xml to gh release create assets**

In the "Create GitHub Release" step (line 107-130), the `gh release create` command currently has only `"$DMG_PATH"` as an asset. Add `dist/appcast.xml` as a second asset. The modified command (note the addition after `"$DMG_PATH"`):

```yaml
      - name: Create GitHub Release
        env:
          GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}
        run: |
          VERSION="${GITHUB_REF_NAME#v}"
          gh release create "$GITHUB_REF_NAME" \
            --title "Automation Health v$VERSION" \
            --notes "## Automation Health v$VERSION

          ### Installation

          1. Download the DMG below
          2. Open the DMG
          3. Drag Automation Health to your Applications folder

          ### Verification

          This release is signed and notarized by Apple. macOS Gatekeeper will allow it to run without security warnings.

          ### Auto-Update

          Existing installations using Sparkle auto-update will detect this release automatically.

          ### Building from Source

          See [README.md](https://github.com/${{ github.repository }}/blob/${{ github.ref_name }}/README.md) for source build instructions." \
            --verify-tag \
            "$DMG_PATH" \
            dist/appcast.xml
```

The appcast.xml is added as the LAST asset. If `dist/appcast.xml` does not exist (e.g., release.sh skipped appcast generation because SPARKLE_EDDSA_PRIVATE_KEY was empty), `gh release create` will fail with a file-not-found error. This is intentional — the release pipeline should not publish a release without an appcast because existing installations cannot detect it. However, to handle the edge case gracefully, the CI also needs `SU_PUBLIC_ED_KEY` injected so the release.sh Step 3c doesn't fail. But SU_PUBLIC_ED_KEY is typically a constant (not a secret) — the developer will add it as a repository variable or hard-code it as a GitHub Secret.

Wait — SU_PUBLIC_ED_KEY is the public key. It's not a secret (it's embedded in the app bundle for anyone to extract). We need to pass it to the release script. Add SU_PUBLIC_ED_KEY injection to the same "Set Sparkle signing key" step:

```yaml
      - name: Set Sparkle signing key
        env:
          SPARKLE_EDDSA_PRIVATE_KEY: ${{ secrets.SPARKLE_EDDSA_PRIVATE_KEY }}
          SU_PUBLIC_ED_KEY: ${{ secrets.SU_PUBLIC_ED_KEY }}
        run: |
          echo "SPARKLE_EDDSA_PRIVATE_KEY=$SPARKLE_EDDSA_PRIVATE_KEY" >> $GITHUB_ENV
          echo "SU_PUBLIC_ED_KEY=$SU_PUBLIC_ED_KEY" >> $GITHUB_ENV
```

**Note on secrets vs variables:** SU_PUBLIC_ED_KEY is stored as a GitHub Secret (not a Repository Variable) to keep all Sparkle credentials in one place. The public key is not secret (it's embedded in the distributed app), but using secrets keeps the CI configuration consistent and avoids the need for an additional variable management step.
